# Capstone 09 - Model Building and Deployment

A reproducible synthetic customer-purchase pipeline: public API collection, immutable raw CSV, cleaning, country enrichment, validation, SQLite star schema, logs and an Excel dashboard.

## Source and allowed choices

The overview suggests Mockaroo, but the rubric's Data Collection row explicitly permits **Mockaroo or public APIs**. This project uses the public Random User Generator API v1.4. Two 5,000-profile responses are retained as original JSON files in `data/raw`. Names, ages and countries come from these synthetic profiles. The six-field `dataset.csv` is generated by `scripts/collect_data.py`. Customer IDs are sequential, purchase amounts are generated in integer cents with a seeded lognormal distribution (mu=9.8, sigma=0.9; bounded 0.01-5,000.00 CAD), and dates are sampled uniformly within 2025. Random seed: 20261028. Amounts and dates are independent of country and age. The data are simulated, not real customers or transactions. Age is the profile age supplied by the API at collection, not a reconstruction of age on each purchase date.

- API documentation: https://randomuser.me/documentation
- Exact URLs, retrieval date, generation rules and SHA-256 hashes: `data/raw/source_manifest.json`
- Country-code/region reference: `data/reference/country_lookup.csv`, a manually authored four-country lookup with standard two-letter codes and descriptive regions.

To reproduce the same CSV from retained JSON, move the existing `data/raw/dataset.csv` and manifest aside, then run `python scripts/collect_data.py`. The collector preserves an existing CSV by default. If original API snapshots are removed, recollection requires internet and may change over time; the included hashes identify this exact snapshot.

The step-by-step instructions explicitly allow CSV/Excel storage, SQLite loading, and **Excel visualization on Windows**. This package uses SQLite plus CSV outputs and an Excel dashboard. It does not contain a Power BI PBIX file. The project title says 'Model Building & Deployment', while its specific modeling task is an analytical schema and ERD; no predictive ML model is required by the supplied steps.

## Pipeline and validation

Raw schema: CustomerID, Name, Age, PurchaseAmount, Country, Date. Grain: one simulated purchase per source row. This snapshot has exactly one row per customer.

1. Read the immutable 10,000-row CSV and compute its hash.
2. Require the exact six-column schema and expected row count.
3. Trim names/countries, collapse repeated name whitespace, cast IDs and ages, parse ISO dates, and parse money as Decimal cents.
4. Reject required blanks, invalid IDs, fractional or out-of-range ages, non-finite/nonpositive amounts, amounts above 5,000 CAD or with more than two decimals, invalid dates, dates outside 2025 and unknown countries.
5. Detect exact duplicates and conflicting duplicate IDs. Conflicts fail immediately; any rejects or exact duplicates block publication. Rejected row details and reasons are written to logs. Nothing is silently dropped into a partial successful dataset.
6. Join the unique country lookup many-to-one; derive country_code, region, year_month, currency, age_group and purchase_category.
7. Load dimension and fact tables in a temporary SQLite database with primary keys, foreign keys and checks. Validate SQLite integrity and foreign keys. Reconcile target count and integer-cent sum with accepted source rows.
8. Close the SQLite connection before replacing the published database, supporting Windows file handling. Write enriched and final CSVs, summary statistics, validation results and real run logs.
9. Recheck the raw hash. A successful final status is recorded only after outputs are written.

Each CSV is replaced through a temporary file. The database replacement is atomic on the same filesystem. The entire set of outputs is not a multi-file transaction; a disk-write failure after database publication may require a rerun. Consumers should read `logs/last_run.json` and use outputs only after a successful run.

### Derived fields and boundaries

| Field | Rule |
| --- | --- |
| age_group | Teen 0-18; Young Adult 19-35; Adult 36-50; Senior 51-120 |
| purchase_category | Low >0-100; Medium >100-500; High >500-1,000; VIP >1,000-5,000 CAD |
| purchase_cents | Exact whole cents parsed from the raw amount |
| currency | CAD for every simulated amount; no currency conversion is performed |
| country_code / region | Many-to-one reference lookup |
| year_month | First seven characters of a validated ISO date |

The worksheet's sample bins exclude zero ages and use an upper age limit of 100. This implementation explicitly supports 0-120 and tests the category boundaries. The current API snapshot has no Teen records; the dashboard keeps the Teen category with a genuine zero count.

## Storage and analytical model

`sql/schema.sql` creates `dim_customer`, `dim_country`, `dim_date` and `fact_purchase`. Fact grain is one purchase, identified by purchase_id. Each dimension has a one-to-many relationship with the fact table, although the included snapshot happens to contain one purchase per customer. Purchase value is stored as integer cents to prevent floating-point reconciliation errors. `analytics_purchases` is a joined view for convenient reporting. `sql/analytics.sql` contains useful country, month and age queries.

- `data/capstone.sqlite`: loaded database.
- `data/cleaned/dataset_enriched.csv`: cleaned and enriched source rows.
- `data/cleaned/dataset_final.csv`: reporting view exported from SQLite.
- `data/cleaned/summary.json`: independently computed SQL aggregations.
- `diagrams/customer_purchase_erd.drawio`: editable draw.io ERD.
- `diagrams/customer_purchase_erd.png` and `.svg`: viewable diagram exports.
- `diagrams/architecture.mmd`: Mermaid pipeline architecture.

## Automation and deployment

`.github/workflows/pipeline.yml` runs tests, the pipeline and the PNG renderer on a main-branch push, a manual workflow dispatch and a daily cron at **12:17 UTC**. It retains logs, cleaned data, SQLite and PNG as Actions artifacts. It deliberately processes the frozen raw snapshot rather than replacing the original data every day. The workflow does not rewrite the Excel workbook automatically. GitHub scheduled workflows may be delayed and require the workflow on the repository's default branch. The configuration is included; **no GitHub-hosted scheduled run has been executed or verified yet**.

For Windows, run `powershell -ExecutionPolicy Bypass -File scripts/register_schedule.ps1` after reviewing the script. It registers an 08:17 local-time Task Scheduler job for the current user. This has not been installed on the student's computer. The machine must be available and the Python installation accessible. Open Task Scheduler and check Last Run Result and `logs/last_run.json` after the first run.

On macOS/Linux, a cron example is `17 8 * * * /absolute/path/to/python3 /absolute/path/to/capstone09-model-building/scripts/pipeline.py`. Use actual absolute paths; this line is not installed by the project. `scripts/run_pipeline.sh` runs both the pipeline and PNG renderer from the project root.

## Monitoring and tests

`logs/pipeline.log` records ingestion, transformation, enrichment, loading, failures and elapsed time. `last_run.json` records the latest run ID, status, UTC timestamps, row count, total cents and duration. `run_history.jsonl` retains successive run statuses. `validation.json` contains reconciliations and raw-file protection evidence. `rejected_rows.json` identifies invalid rows; the valid supplied snapshot has none.

Five unittest methods cover category boundaries; whitespace cleaning and exact duplicates; null, type, range, money, date and reference failures; conflicting IDs; and a full 10,000-row integration test. The integration test verifies idempotent output, raw-byte preservation, row/money reconciliation, failure status/logging, and preservation of the previous database and final CSV after invalid input. Test fixtures run in a temporary directory, separate from the supplied successful output. See `logs/test_results.txt`.

## Excel dashboard and refresh

The Excel workbook has three sheets: Dashboard, Summaries and Data. Four native charts show purchase value by country, monthly value, spending-category counts and age-group counts. SUMIFS/COUNTIFS formulas derive summaries from the full Data table. Headline totals are linked to those formulas. All 10,000 records are included, dates are numeric Excel dates, and amounts/counts are numeric. Workbook totals were reconciled to SQLite, formula errors scanned, and changing an input cent value was verified to update the summary before restoring it. Every sheet was visually checked. Desktop Excel itself was not available for application-level verification.

The workbook is a saved snapshot with live internal formulas, not a live database connection. After rerunning the pipeline with changed values, import `data/cleaned/dataset_final.csv` in Excel and replace Data!A5:N10004 in the existing field order (dates must remain dates, not text); the 10,000-row formulas and charts recalculate. Row counts other than 10,000 require formula and table-range updates and are rejected by the default pipeline. `python scripts/render_dashboard.py` regenerates the PNG directly from the validated summary. The static PNG is also included for viewing without Excel.

## Findings and limits

The included synthetic snapshot has 10,000 purchases totaling **CAD 2,681,993.06**, averaging **CAD 268.20**. The United States has the largest simulated country total (CAD 695,220.29), followed closely by the United Kingdom (CAD 692,012.05). May has the largest simulated monthly total (CAD 244,200.33). The Medium category contains 6,185 purchases. These are descriptive facts about the generated snapshot, not evidence about real countries, age groups or customer demand. No causal, predictive or commercial conclusion is justified.
